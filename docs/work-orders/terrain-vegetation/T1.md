### Settled design

These decisions are settled here from the code. Implementer WOs follow them. T1-0 settles only the points listed under it.

**D1. Load ordering and publication.**
- One owner, a C# static `WorldGeneration` (new file `scripts/Terrain/Generation/WorldGeneration.cs`), holds `Current`: an immutable `WorldGenerationState(int Generation, int FeatureMask, string[] ReviewFeatures, string Source)` behind a volatile field. The default before any publication is generation 1, mask 0, source `"default"`. That default covers harnesses that build the game scene without the launcher, such as `tools/tree_cpu_profile.gd`.
- `Publish(TerrainGenerationParameters? recipe, string source)` sets `Current` and calls `RenderingServer.GlobalShaderParameterSet("ringworld_world_features", mask)`. A null recipe or a pre-v9 recipe gives generation 1 and mask 0.
- GDScript reaches it through a new `WorldGenerationBridge : RefCounted` (`scripts/Terrain/Generation/WorldGenerationBridge.cs`), preloaded by the launcher like `TERRAIN_GENERATION_SAMPLER`.
- Publication points (main thread, both before `add_child`):
  - (a) the top of `_configure_game` (launcher line 1541): publish `pending_surface_generation_recipe_json` when the runtime surface backend is selected and the JSON is non-empty, otherwise publish legacy;
  - (b) the top of `_configure_mega_ring_game` (line 1175): publish legacy.
  These cover `_start_game` (line 1088), the diagnostic game, the warm menu world (it goes through the launcher, spec section 1, item 2) and every launcher-driven harness (fact 7).
- Every settings owner and renderer reads after `add_child` (fact 8), so it sees the published value. Each publish replaces the previous one (one world at a time), and there is no reset on unload.
- Worker threads read the mask from their sampler (D5), not from the static.

**D2. How tests pin a generation.**
- Launcher-driven harnesses use the project setting `ringworld/runtime/surface_world_generation` (int; not declared in `project.godot`, like the v7/v8 settings):
  - unset or `-1`: the default;
  - `0`: legacy, the pre-v9 recipes chosen by the v7/v8 toggles exactly as today;
  - `N >= 1`: new runtime-generation worlds with landforms and the Weather Lung on are created as v9 at generation N.
- The default when unset is `WorldGenerationLedger.LatestFrozen`, **except** when `surface_landforms_v7` or `surface_weather_lung_v8` is set false. Then the default is `0`, so every harness that already pins v6 or v7 (for example `shadow_harness_common.gd:229-230`) keeps its exact recipe with no edit.
- Review features for tests and tools: `ringworld/runtime/surface_review_features` (comma string, default empty). It is honoured only when the target generation equals `LatestFrozen` and `OS.is_debug_build()`.
- Helper `tools/world_generation_pin.gd` (`extends RefCounted`, static `pin(generation: int, review := "")` and `unpin()`). Harnesses call it before instantiating the launcher.
- Headless C# tests use the new `EmitterSiteTestWorlds` methods (T1-4): `Gen17WorldRecipe(seed, generation, review = null, climate = false)`, `CreateGen17World(...)` and `CreateProductionSettings(seed, recipe)`.
- Rule for new tests: name the generation explicitly and never use "latest".
- Existing launcher-driven tests that would silently move to v9 and assert a v8 identity pin `0` (inventory in T1-6). That is a test edit, never a golden edit.

**D3. A second settings file for generation-specific defaults** (needed first by vastness V1, plan 2.2 "Settings", vastness 11.3).
- New static `WorldGenerationSettingsFiles.Resolve(string userPath, int fromGeneration) -> string` in `scripts/Terrain/Generation/WorldGenerationSettingsFiles.cs`:
  - if `WorldGeneration.Current.Generation < fromGeneration`, it returns `userPath` unchanged;
  - otherwise it returns the sibling `<stem>_g<NN>.tres` (NN = `fromGeneration`, two digits). If that file does not exist and `userPath` does, it copies `userPath` to it once (no overwrite) and returns it.
- It never writes `userPath`.
- An owner that needs generation-specific defaults passes the result to its constructor (for example `new AtmosphereVisualDefaults(path)`). Since owners are created after publication (D1), the file in use is fixed per world load.
- The new generation's changed default values are applied by that owner's own migrate step when the file is first created (the step's own WO).
- `Install*Defaults(path)` overrides from harnesses bypass it.
- No menu row and no toggle. T1 adds the helper and its test; no owner calls it yet.

**D4. Recipe v9 fields.**
- The id is `ringworld_surface_world_v9`. The field set is the v8 `LandformFields` plus:
  - `world_generation` (int, `>= 1`);
  - `review_features` (string: sorted, unique, comma-joined feature ids, each matching `^[a-z][a-z0-9_.]*$`; empty for a normal world);
  - the climate base fields (names, list and defaults: T1-0, C1).
- Canonical JSON is the v8 canonical body with the new id, followed by `,"world_generation":N,"review_features":"..."` and then the climate segment.
- `TerrainGenerationParameters` gains `WorldGeneration` (1 for every pre-v9 id), `ReviewFeatures` (empty for pre-v9) and `IsWorldGenerationRecipe`.
- Every `Has*` property includes v9 exactly as v8: "the model treats v9 as v8".
- Structural validation lives in the parameters type (`FromJson`). Ledger validation lives in `WorldGenerationLedger.Validate(parameters, out string error)`: the generation is at most `LatestFrozen` and at least the retirement floor (1 today), and every review feature is known and not already in the base generation. The launcher calls it on load and on create, so a retired or unknown feature produces a clear error instead of a parse failure.
- A string, not an array, because `FromDictionary` (fact 1) and the GDScript bridge carry only String, Int and Float.
- Fields added by later steps follow D9. The T1 field set above (D4) is the fixed base of every v9 recipe.

**D5. Ledger, mask and shader global.**
- `scripts/Terrain/Generation/WorldGenerationLedger.cs` (static) holds:
  - `Features`: `FeatureInfo(string Id, int Bit, string Plan, int FrozenIn)`. `FrozenIn` is 0 while the feature is open. Bits are 0..30, assigned when a feature is added, never reused.
  - `Rows`: `Row(int Generation, string Step, string[] Features, string Frozen)`.
  - `LatestFrozen`, `RetirementFloor`, `FeatureSet(int generation, IReadOnlyList<string> review)`, `MaskFor(int generation, IReadOnlyList<string> review)`, `Has(int mask, string id)`, `Validate(...)`, `CreateForTests(...)`.
  - The ledger file (all of the above, including `Validate`) is built in T1-1, because the recipe and `WorldDefault` need it (D9, D10). T1-3 adds the owner, publication and the bridge.
- Production T1 content: one row (generation 1, step `"baseline"`, no features) and an empty feature list.
- The mask goes in the `int` global `ringworld_world_features` (declared in `project.godot` `[shader_globals]`, type `int`, value 0).
- `RingTerrainSampler` gains `WorldFeatureMask` and `WorldGenerationNumber`, derived once from its recipe (0 and 1 for non-runtime or pre-v9 samplers). The tree and grass builders and the proxy sectors reach it through the sampler they already hold (fact 10).
- Compute shaders are **not** changed in T1. Each later feature adds the bit to its own parameter buffer when it first needs it (plan 2.2, vastness 11.3). No GLSL or `.glslinc` edit in T1.

**D6. Fingerprint keying.**
- Golden row 1 stays the v8 row (generation 1 means "every recipe up to v8").
- `world_generation_fingerprint_test` additionally computes the row content for a v9 recipe at generation 1 (seed 1337, production settings) and requires every content field (`heights`, `sampler`, `trees`, `grass`, `grass_params`, `scatter`, `catalog`) to equal row 1. Only `generation` label metadata, `generator_id`, `definition_hash` and `captured` may differ.
- Rows for generation 2 and later are computed from v9 at that generation and compared in full.

**D9. How a later generation adds v9 recipe fields** (needed by T7-3's meso-relief fields and by any later step). Generation N's recipe JSON and definition hash never change when a later step adds fields.
- Every v9 field added after T1 is an **extension field**, declared once in the append-only C# table `WorldRecipeFields.Specs` (new file `scripts/Terrain/Generation/WorldRecipeFields.cs`). Each entry is `RecipeFieldSpec(string Name, string FeatureId, RecipeFieldKind Kind (Int or Float), double Default, double Min, double Max)`. The owning feature is a ledger feature (D5).
- **Active rule.** An extension field is *active* for a recipe when its `FeatureId` is in `WorldGenerationLedger.FeatureSet(world_generation, review_features)`: the features frozen at or below that generation, plus the recipe's review features.
- **Serialisation.** Canonical JSON is the T1 v9 body (D4), then the active extension fields in table order. Inactive fields are **not serialised**. So a generation-N recipe built before or after a later step has the same JSON, because features frozen later have `FrozenIn > N`.
- **Parsing.** An active field is required, within its range and of its kind. An inactive field that is present is rejected as unknown. There is no silent default on parse. The `Default` is used only by the recipe factory (D10) when it builds a new recipe.
- **Model behaviour when inactive.** The model takes the feature-off code path (the generation-N behaviour), gated by `TerrainGenerationParameters.HasWorldFeature(featureId)`, exactly like `HasLowlandLandforms` today. No field value is consulted.
- **Freeze rule.** Once a feature is frozen, its extension fields are final: no additions, removals, renames, reorders or range changes. A later change is a new feature with new fields in the next step (plan 2.2 "After a step is frozen"). An open feature's fields may change freely, because review worlds are disposable.
- **One source of truth.** GDScript does not mirror the table. `terrain_generation_recipe.gd` keeps extension values in `extension_values: Dictionary` and emits exactly the active names, which it gets from the existing C# bridge `TerrainGenerationSampler` through a new `ActiveRecipeFields(generation: int, review_csv: String) -> Array` (each item `{name, kind, default, min, max}`). A preview or menu built later (for example T7's sliders) reads ranges from there too.
- **Test-only schemas.** `FromJson` and the factory take an optional `WorldRecipeSchema` (a ledger plus a spec table), whose default is production. Tests exercise the rule with a synthetic schema without mutating production statics.
- **Golden.** `tools/fixtures/world_generation_recipe_golden.json` stores, per frozen generation and per seed (1337, 90210, 2147483000), the canonical JSON SHA-256 and the definition hash of `WorldDefault`. It is append-only like the fingerprint golden: `--capture --generation=N` appends, never rewrites. `world_generation_recipe_test` compares every row, so any change to an earlier generation's recipe JSON fails (T1-1).

**D10. Recipe-at-generation helper.**

**D11. Generation options in the landscape harness.** Any landscape or vastness audit can run on a chosen generation or set of review features. The default is unchanged: the pinned v8 world, which is generation 1.
- C#: `LandscapeWorld.For(int generation, IReadOnlyList<string>? review = null) -> LandscapeWorld.Spec` holds `Recipe`, `CreateSettings()`, `CreateSampler()`, `CreateShapedModel()`, `CreateNaturalModel()`, `CreateWorkers(int count)`, `Tag` (`"g01"`, `"g02"`, `"review-<ids>"`) and `IsDefault`.
  - `LandscapeWorld.Default` is the existing pinned v8 world. All existing statics delegate to it unchanged.
  - Generation 0 in flags means `Default`. `--generation=1` explicitly means v9 at generation 1 (identical terrain, different JSON).
