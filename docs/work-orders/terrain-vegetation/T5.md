### Tree tile pipeline (`scripts/Voxel/LOD/RingBiomeDecorationLayer.TreeStreaming.cs`)

- P1. `BuildVegetationTile` (lines 1099-1183). Order:
  - disk load first, under the scope "Trees disk load" (1104-1112);
  - generation under "Trees build" (1113);
  - `sampler.EnablePresentationLatticeCache()` memoises the 2 m lattice on the build's private sampler copy (1115);
  - loop over 30 m cells times candidates (1124-1172), with hashed jitter (1130-1131);
  - rejects water, non-Forest or Grassland biomes, and `SiteMask.BlocksVegetation` (1139), plus root support (1140);
  - slope from plus or minus 2 m probes (1142-1144, 1269-1277); regional density (1145-1151);
  - Matern-style spacing with a stable-id tie break (1162, 1185-1222), local radius 2.5-9 m (1256-1261);
  - species and variant (1163-1164), scale 0.85-1.15 (1165).
- P2. Tiles are 240 m: 8 cells of 30 m. Production builds its request at lines 487-512; the review helper used by the fingerprint is `BuildImportedForestReviewTile` (25-39), with 30 m, 8 cells and 12 candidates.
- P3. Records and format:
  - `CachedTree` (line 64); file magic `VTG2`, version 4 (59-60), at most 8,192 trees per tile (61);
  - the loader validates variant ranges per species (1329-1333); the writer is at 1340-1395.
  - **A new record type belongs in its own file and format; do not widen `CachedTree`**, or generation 1 cache files change format.
- P4. Cache identity, `ResolveVegetationDiskCachePath` (608-639):
  - includes the cache version, generator version, seed, `TerrainDefinitionHash` (632) and a settings hash (1498-1528), which mixes in `ForestRegionSampler.AlgorithmVersion`, `ImportedTreeCatalog.CatalogVersion` and `VariantCount`;
  - new generations get separate caches once T1's v9 definition hash covers `world_generation` and `review_features` (plan 2.2) **(verify in T1.md)**;
  - code changes inside an *open* feature do not change the hash, so review worlds would load stale tiles. Use an algorithm version constant in the scatter cache key, or no disk cache for open features.
- P5. Rank gates: `VegetationLodRankGate` (1478-1486) keeps a rank-prefix subset per LOD. That pattern lets a density setting filter without re-placing.

### GPU vegetation path

- P6. `scripts/Voxel/LOD/RingGpuVegetationCompute.cs`:
  - `BatchRegistration` (29-31) has a single `Grass` flag, so there are two modes, grass and tree;

  - `HazeChannel` (192). Channels exist only for Grass and Trees (`scripts/Atmosphere/RingVegetationHaze.cs:20`); other batches fall back to per-vertex haze (plan 1.2).
- P7. Tree layer, `scripts/Voxel/LOD/RingBiomeDecorationLayer.Gpu.cs`:

  - `MaximumGpuTreeRoots` 65,536 and `MaximumGpuTreeBatches` 1,024 (20-21); per-LOD caps in `GpuTreeLodCaps` (972-979);
  - outputs are keyed per (tile, variant) group and LOD (`GpuGroupKey`, `GpuOutputKey`, 59-60), with merged mid and far groups (228-233). **One draw per group, variant and LOD**, so draw count grows with the number of distinct meshes times tiles unless merged.
- P8. The shared far tree impostor packs exactly 30 LOD3 meshes (`scripts/Vegetation/ImportedTreeImpostorCatalog.cs:26`; `materials/imported_tree_impostor.gdshader:61` clamps the variant to 0-29). Rocks must not enter it.

### Cost, re-checked against T0 8.6

- C1. Plan gates (A1000, Medium): 0.5 ms GPU; 24 draws; at most 1,500 boulders, 150 outcrops and 6,000 cobbles resident; tile build at most 1.3 times the tree-only tile; under 8 MB of mesh data.
- C2. Tile build. The 4070 "Trees build" medians are 8.9 ms (plains), 9.6 (hills), 9.7 (coast), 14.8 (forest interior), 15.0 (edge) and 19.5 (clearing) per tile, on a worker; the 1.3x gate allows +2.7 to +5.9 ms.
  - A naive 8 m habitat grid over a 240 m tile, with a halo wide enough for 64 m curvature, is about 47 x 47 = 2,209 height samples. At 1.15-2.8 us per sample (plan 1.2, v7 cost; est.) that is 2.5-6 ms, about the whole gate before any placement.
  - **The grid design must reuse samples**: align to the memoised 2 m lattice (P1), take 64 m curvature from a coarser sub-grid, and share between tiles or layers where it can.
- C3. Draws. T0 draw deltas include shadow-pass draws (trees: 151-749 at forest poses). Batching rocks per mesh and LOD across tiles gives up to 30 meshes x 3 LODs = 90 draws before shadows, against a gate of 24. T5-2 must show how the gate is met, for example by drawing all rock variants of one LOD from one shared mesh with vertex fetch, the way the tree impostor packs 30 variants into one mesh (P8). It must also state whether the 24 counts shadow-pass draws. **Ask the user if the gate cannot be met** (see the user decisions in the parent report).
- C4. **How T5 measures cost.**
  - GPU: a new hide class `scatter_hidden` in `tools/landscape_baseline_common.gd` (lines 20-21): every scatter renderer and its shadow casters, same-boot A-B-A in a review world. Draw and primitive deltas are exact.
  - CPU tile build: a separate scope "Scatter build" nested in "Trees build". The gate compares "Trees build" median and p95 in the review world against the same poses in a generation 1 world.
  - Memory: the prepared rock resource size plus resident instance bytes.
  - The A1000 is authoritative; the 4070 is indicative (T4 C3).

ROLE: sol_lead (design)
SIZE: M
DEPENDS ON: T4-1 (rock exposure rule D2), T1 merged

OBJECTIVE
A "T5 design A" section appended to this file. It fixes the habitat field grid, the class table schema, the record and cache format, determinism rules and the tile-build cost plan, for T5-3 to T5-5 and T6 to implement.

CONTEXT / ROOT CAUSE

FILES/SYMBOLS
Read: P1-P5, P10, P12, P13, `scripts/Voxel/LOD/RingGrassTileBuilder.cs` (grass tile inputs, lines 109-341), `RingTerrainSampler` presentation lattice cache, T4 design D2 and D5. Write: this file only.

REQUIRED CHANGES
Write decisions A1-A9, each with the choice, the reason and exact names.
1. A1 Grid definition.
   - A canonical global 8 m lattice. Every field value is a pure function of its lattice node and the world, never of the tile that asks, so any tile, layer or worker gets bit-identical values.
   - State the wrap at the ring seam and the clamp at the rim (across is not wrapped, as in `ForestRegionSampler.cs:54-55`).
   - Define the value between nodes (bilinear) for placement.
2. A2 Fields and formulas, from plan 2.1:
   - slope, and curvature at 8 m and 64 m (P12: say what 8 m curvature contributes before T7);
   - wetness without rivers (moisture, concavity), with a slot reserved for "height above nearest channel" that T5-11 fills;
   - rock exposure, using T4 design D2's rule so terrain and meshes agree;
   - soil depth as its complement;
   - canopy cover from `ForestRegionSampler`.
   - Give ranges and the C# struct (for example `RingHabitatSample`).
3. A3 Sampling cost (C2). Show the sample count per 240 m tile and per 32 m grass tile, and how the design fits the 1.3x gate: alignment to the memoised 2 m lattice, a coarser sub-grid for 64 m curvature, the halo, and any per-tile in-memory reuse. State the expected added milliseconds against the C2 medians.
4. A4 Who computes the grid.
   - Tree tiles compute it for their own classes.
   - Say how the grass builder (T6) gets fields for its 32 m tiles: recompute its own patch, or read a shared in-memory cache. Recomputing is preferred if it fits, because it keeps the layers independent.
5. A5 Class table schema. One append-only table with stable ids. Per class:
   - the response to the habitat fields (a density curve per field);
   - the spacing radius and its candidate cell size;
   - the size distribution and alignment (upright, slope-aligned, bedding horizontal);
   - reach and LOD distances;
   - collision shape, far term and resident cap.

6. A6 Records and cache.
   - A new record struct (id, around, across, surface height, class id, mesh index, scale, yaw, tilt if needed, rank).
   - Its own file next to the tree tile (for example `s_<around>_<across>.bin`) with its own magic and version.
   - A `ScatterAlgorithmVersion` in the key so open-feature changes cannot load stale tiles (P4).
   - Edits: follow the tree tile's edit-version and edited-column rules (lines 481-486, 641).
   - Records are built only when the feature is on.
7. A7 Generation 1 path. `BuildVegetationTile` stays byte-identical for worlds without the feature. The scatter builder is a separate function called from the same worker task after the trees. Trees in a `scatter_rocks` world are unchanged (T6 changes them, behind its own feature). Show that the fingerprint tree rows cannot move.
8. A8 Determinism and seams: stable ids from the canonical cell, class and candidate; ties by id; halo regeneration as in `WinsForestSpacingCompetition`; worker-count independence.
9. A9 Fingerprint: what the `scatter` slot hashes from generation N on (per T1's generation-keyed computer), and at which tiles (the eight T0 poses plus one dressing pose with rock).

DO-NOT-CHANGE CONSTRAINTS
Design only. Stay within plan 2.1 and 5. If the 1.3x build gate cannot be met by any design, say so with numbers rather than relaxing it.

VALIDATION STEPS
